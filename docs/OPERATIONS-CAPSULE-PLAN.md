## 1. 目标与优先级

设计原则：总开关开启后，微信前台始终有一个可找到、可展开、不抢操作的运营入口；捕获、选组、发送、暂停、完成形成完整流程，不让用户反复进入设置页。

用户明确的要求：
- 这是常驻运营胶囊，不是发送期间才显示的进度条；本组结束不能消失。
- 靠近左右边缘，拖动后吸附，可半隐藏，但应始终留有可点击入口。
- 自动化指自动捕获指定母群、指定 wxid、指定类型的消息，不是自动启动发送或自动接下一组。
- 转发时可在微信前台聊天、回复消息和查看视频号。
- 统一保存条件、自动分组、搜索排除，尽量减少日常手动设置及确认步骤。

本计划是运营胶囊及自动捕获联动的最新开发基线。旧文档中“完成后隐藏”“回前台必须重新手动开启捕获”“每次进入设置页等待”的描述，仅保留为旧版本行为，不用于本阶段目标。发送恢复仍必须手动，不能与捕获恢复混淆。

## 3. 范围与不做事项

本阶段包含：账号级运营总开关、前台自动捕获、唯一源消息占用、常驻胶囊、贴边收纳、消息预览与分组入口、发送控制、完成反馈、持久恢复、运行诊断和回归测试。

本阶段不做：后台持续发送、规则自动接力、失败/未知自动重试、多消息无限队列、100/200 群实发扩容、多个母群同时运行、多账号调度、视频/文件转发。

## 4. 开关、账号和生命周期

| 场景 | 胶囊 | 捕获 | 发送 |
| --- | --- | --- | --- |
| 默认/总开关关闭 | 不显示 | 不监听 | 禁止新派发 |
| 首次开启 | 校验保存配置后显示 | 没有占用内容时开始监听 | 不启动 |
| 微信前台空闲 | 等待消息/完成摘要 | 自动监听 | 不启动 |
| 收到第一条有效消息 | 待转发提示 | 锁定该条，停止接纳下一条 | 不启动 |
| 用户选组并开始 | 显示本组进度 | 不替换源消息 | 仅启动该组 |
| 后台/锁屏 | 不显示，保留开关 | 停止监听 | 暂停，不新派发 |
| 回前台/进程重启 | 恢复当前账号状态 | 开关开且无占用内容时自动恢复监听 | 只显示待继续，绝不自动恢复发送 |
| 当前组完成 | 保留完成摘要及下一组入口 | 当前内容还有未结束分组时保持占用 | 不自动接下一组 |
| 关闭总开关 | 移除 | 停止且使旧回调失效 | 暂停并保留进度，在途回调正常收尾 |
| 账号变化/无法核对 | 先隐藏旧账号内容 | 旧监听失效，不自动跨账号启用 | 停止新派发，记录保留在原账号 |

默认方案：总开关按稳定账号持久保存；账号无法确认时不能展示旧内容或启动监听。账号变更后先进入安全关闭状态，用户在该账号设置页开启。仅应用重启、同账号恢复时使用已保存开启状态。

“悬浮入口”旧开关只控制旧设置快捷入口，不再控制运营胶囊。设置页保留“我 → 设置 → SyncRelay 转发”；运营总开关和旧快捷入口文案必须明确区分，避免两个相似开关相互覆盖。

关闭开关不能删除预览、计划或历史，也不能把已派发消息写成取消成功。重新开启时优先恢复原内容和待继续状态，不捕获新内容覆盖它。

## 5. 源消息与分组的完整闭环

1. 用户保存母群、来源成员 wxid（含本人）、类型、间隔、排除群和分组，开启总开关一次。
2. 监听所有符合已保存条件的新候选；不依赖设置页存在。来源、账号、类型、插件自产消息过滤沿用既有核验。
3. 第一条符合条件的消息成为唯一候选；图片在资源准备完成前显示“图片准备中”，不能假装已可转发。
4. 候选及冻结配置在显示“已捕获”前完成持久保存；消息唯一键为账号 + 母群 ID + 服务器消息 ID。重复 hook/同步回调不生成第二条内容。
5. 点击胶囊进入“内容摘要 + 目标分组”运营面板，可查看完整文字或图片。选择一组后用一个明确的“开始转发”动作完成必要计划确认与启动，不要求额外前往历史页建计划，不逐群确认。
6. 如计划建立成功而启动失败，保留该计划和准确原因；重试开始不得重复建计划。双击、晚回调、再次打开面板不能创建重复运行。
7. 同一内容供全部分组复用；本组完成后，仍可选下一组，绝不重新捕获后再发下一组。
8. 默认方案：所有分组处理结束后解除内容占用并自动继续监听，胶囊保留最近完成摘要直到新事件到来。若还有未发分组，用户可明确“结束本次内容”，提示剩余范围后归档并恢复监听。
9. 放弃候选后自动恢复监听，但持久记住该候选已处理/放弃，避免同一旧消息立即再次触发。缓存和去重记录采用有界清理，不清除已有发送占位来换取重发。

不得静默排队或覆盖后续消息。占用内容期间停止接纳新候选，并在面板注明“当前内容处理中，新消息暂不捕获”。本阶段不承诺补抓后台、退出期间或占用期间的历史消息。

新旧消息边界是必须实现和测试的技术门槛：验证宿主可用的消息时间/同步标识及消息 ID 去重；不能单凭回调到达时间把离线补同步当新消息。缺乏可信依据时显示来源待核对，不擅自放宽成持续误捕获，也不得标注“自动捕获完成”。

修改配置默认只在保存后生效。已有候选、计划或运行使用自己的冻结配置；保存新条件不能改写当前内容。需要切换时显式结束/放弃当前内容，旧监听代次失效，新条件重新监听。取消编辑不打断原配置工作。

## 6. 胶囊状态与操作

胶囊可见性由“运营开关 + 当前账号可信 + 微信前台”决定，不由 busy 决定。业务状态、捕获状态、显示形态独立建模，不用一个布尔值包办。

| 业务状态 | 展开文案示例 | 主操作 |
| --- | --- | --- |
| 等待消息 | 等待母群消息 | 打开运营面板 |
| 图片准备 | 图片准备中 | 查看状态/放弃 |
| 待转发 | 新文字/图片 · 待转发 | 查看内容并选组 |
| 运行 | 第 1 组 · 12/20 | 暂停 |
| 暂停收尾 | 正在暂停 · 12/20 | 等在途结束，不允许重复继续 |
| 暂停/待恢复 | 已暂停 · 12/20 | 继续未尝试目标 |
| 本组完成 | 本组处理完成 · 20/20 | 查看结果/选择下一组 |
| 当前内容结束 | 本次处理完成 · 等待新消息 | 查看完成摘要 |
| 捕获故障/执行异常 | 暂停原因的简短摘要 | 查看原因及可用恢复操作 |

已处理数包含已提交、确认、失败、未知及取消，详情分开展示；不能把 20/20 写成“全部送达”。异常标记优先于绿色完成标记；失败/未知不自动重试。最近完成时间使用存储中的实际 ended_at，不取打开页面时间。

分组列表显示：组名、目标数、本次内容的进度、状态、完成时间。以本次内容/规则/运行 ID 关联，不把两条不同源消息的统计混在一起。“今日累计”后续另做定义。

## 7. 吸附、收纳与视觉约束

方向固定：贴合微信原生 UIKit、克制的状态色、清晰的中文文案；不做独立品牌大浮层。本文件只交互规划，尚未渲染或真机视觉验收。

默认方案：
- 展开胶囊 + 贴边小标签两态；空闲约 5 秒收纳，值集中管理，后续可根据手感调整。
- 松手吸附最近的左右边缘，记住边缘及安全区内的相对纵向位置；半隐藏仅是视觉收纳，不能完全拖出屏幕。
- 可点击范围至少 44pt，避开微信返回边缘手势；只接管胶囊自身范围的触摸，不铺全屏透明遮罩、不创建抢焦点窗口。
- 收纳状态点击只展开，不直接触发发送、暂停或继续；拖动越过阈值后取消点击判定。
- 记住位置，横竖屏、键盘、刘海/底部安全区变化后重新约束；临时键盘避让不覆盖用户原先位置。
- 捕获、完成、异常各短暂提示一次；不强制弹窗、不抢键盘、不自动弹完整面板。异常/待转发提示点保留到查看。
- 运行时贴边仍可识别进度，完成时仍可找到结果。视频号默认收纳，不保证所有全屏布局都无冲突，必须实机验证。
- 三类轻动效：拖动松手吸附、胶囊展开/收纳、状态切换；遵循“减少动态效果”，不循环闪烁。
- VoiceOver 可读出状态及操作，动态字体不裁切；隐私模式默认不在贴边标签显示正文、wxid 或群名。

## 12. v2 产品结构与联动定稿（2026-10-22）

本节汇总用户在新开发会话建立后继续确认的要求。它不是可选灵感清单；实现必须按阶段纳入，不能以旧版范围排除已确认功能。尺寸、收纳时间、视觉细节仍可在真机验证后调整。

### 12.1 总开关的前置条件

- 必须在插件内完成并保存母群、来源成员 wxid、类型、有效间隔以及至少一个含有效目标的分组，才允许开启。仅“保存过配置”不够。
- 关闭状态不捕获、不新派发；关闭不是删除记录，重新开启不是重新发送。
- 配置不完整时显示缺项及对应入口；运行中无法核对账号或配置有效性时停止新派发并说明原因，不能绕过校验。

### 12.2 三个页面的固定结构

唯一快捷入口为运营胶囊。页面关系：胶囊 → 运营首页 → 分组列表/执行详情；微信设置 → SyncRelay 设置页。不要另建第二个悬浮设置球。

**运营首页**：顶部“关闭 / SyncRelay 运营 / 设置”；正文依次为运行状态、当前内容、分组概览、最近一次结果。当前内容显示摘要/缩略图，可看完整内容。待转发时主操作为“选择分组转发”；运行时为当前组进度、暂停及详情；暂停时为继续未发及详情。关闭页面不停止捕获、不暂停发送。总开关只在设置页操作，首页关闭状态提供前往设置入口。

**分组列表**：顶部显示当前内容和捕获日期时间；支持按组名/群名搜索，以及全部、未开始、进行中、已完成、有异常筛选。每组显示名称、实际目标数、本次内容进度、状态和相应操作。没有源内容时可查看群名单但不能发送；当前有占用任务时其他组不能开始。超出本版 20 群执行范围的组直接说明限制，不偷偷截取。

分组状态：未开始 → 开始转发；运行 → 暂停；暂停收尾 → 等待在途结束；暂停/重启待继续 → 继续未发；处理完成 → 查看结果；主动取消 → 已取消/查看结果。详情查看本次执行，管理修改以后使用的分组，两者不能混淆。普通继续与主动重新发送必须是不同入口。

**设置页**：保持微信原生分组列表和不透明导航栏，分区固定为：运行（总开关、配置缺项、运营首页入口）、消息来源、发送间隔、目标分组、运营胶囊、备份与恢复、维护与关于。修改保存按钮叫“保存”；离开未保存配置需提醒。设置页关闭不暂停运行，保存新配置不自动续发。

日常流程固定为：配置一次 → 开启总开关 → 自动捕获 → 胶囊提示 → 查看内容/选组 → 手动开始。必要的计划建立在内部完成，不要求先走独立“确认建立计划”页面，不逐群复核。

### 12.3 完成时间必须包含日期

- 分组列表和执行详情统一显示 `完成于 2026-10-22 21:08`，包括日期和时间；跨天后仍完整显示。
- 手动结束/取消显示对应状态及 `结束于 2026-10-22 21:08`，不得伪装成处理完成。
- 采用持久化实际结束时间，不用页面打开时间。时间戳独立存储，显示按设备本地时区转换；时区变化只改变展示，不改变原始记录。
- 本次内容/分组/运行相互绑定，不把不同内容的完成时间和进度混在一起。详情区分已提交、确认、失败、未知和取消；处理完不等于全部送达。

### 12.4 短胶囊及按场景切换

胶囊不能做成长条工具栏，不放长组名、母群名、wxid、正文或完整日期。固定三种形态：日常贴边小标签；运行/暂停的短胶囊；设置页/运营面板内的状态栏加收纳边缘入口。进入页面仅切换形态，不改变业务运行状态。页面与胶囊消费同一状态快照。

- 运行短胶囊：`12/20  暂停  ⋯`。
- 暂停短胶囊：`12/20  继续  ⋯`，暂停仍显示进度及操作菜单。
- 菜单包含“查看本组详情”“进入设置”“取消本组发送”。进入设置不恢复暂停任务。
- 待转发/完成/异常简短提示：`新图片 · 查看`、`已完成 · 查看`、`有异常 · 查看`；提示后可收纳，但入口不消失。
- 设置页/运营面板显示完整状态，浮动控件收纳，不覆盖保存、返回、输入框和开关。退出页面恢复对应短胶囊/标签。
- 位置吸附、键盘避让、点击/拖动区分、44pt 触控与安全区原则沿用第 7 节；布局不能因长文本或大字体无限加宽，也不能单纯缩小文字硬塞。
- 业务状态优先级与展示形态分离：在途收尾时禁止重复继续；异常不能被完成标记覆盖；等待监听时可在首页查看最近完成结果。

### 12.5 暂停、取消与重新发送的区别

暂停保留原批次未尝试目标；取消本组结束该运行且取消未派发目标，本次运行不能再直接继续。取消不关闭总开关，不丢弃源内容，其他组仍需用户主动选择，不自动接力。

取消前仅一次必要确认：“取消本组剩余发送？尚未发送的目标将取消；已提交的消息无法撤回，在途消息仍可能发送完成。其他分组不会自动开始。”确认后阻止新 claim；已有在途结果正常收尾，不能全部写成取消成功。若存在在途项，先显示“取消收尾中”，收尾结束后显示最终已取消状态及统计。

取消后胶囊仍可查看，分组显示已取消和结束日期时间。设置修改默认只影响后续内容，不能改写当前冻结快照。明确的人工排除是对当前未发目标的撤销授权例外，见 12.7。

### 12.6 持久去重与 pending 语义

用户明确要求：除非主动点击“重新发送”，否则不能重复多发同一条消息到同一群。

| 状态 | 普通继续的行为 |
| --- | --- |
| pending，尚未尝试 | 按原队列发送一次 |
| submitting，在途 | 等结果，不再次提交 |
| submitted/confirmed | 跳过 |
| failed/uncertain | 不自动重发 |
| 用户取消/排除的未发目标 | 不因继续或重新开启而恢复 |

继续只消费原任务 pending，不重建全量列表、不清 claims、不把已尝试目标退回 pending。发送前先持久登记尝试再调用宿主；进程中断不能因为缺回调就再发。不能承诺网络端 exactly-once，但普通恢复必须避免重复提交。

去重范围至少为账号 + 源群 + 源服务器消息 ID + 目标群，跨分组、重启、重建计划均生效。以当前配置或不同分组 ID 作为唯一去重依据不够。

“重新发送”属于新增明确功能，覆盖第 3 节中将主动重发暂缓的旧范围描述：放在详情的次级操作中，先展示目标范围和重复风险，由用户确认后创建有唯一 ID、关联原记录的新批次。不得清除旧记录或复用普通继续实现。总开关、账号校验、单运行互斥、20 群上限仍适用；没有就绪内容/素材时拒绝重发。选定范围一次冻结，未选目标不得隐含加入，重复点击确认不能创建多个批次。

### 12.7 新群自动分组与人工排除

自动分组时提供“新群自动加入分组”，这是按账号持久保存的长期开关；设置页和自动分组页读写同一份偏好。默认关闭，开启后无需逐群弹确认，优先填未满组，全部满时新建同规格逻辑分组，不创建微信群、不自动发送。关闭后新群留待人工分配。

本条覆盖第 3 节将新群分配整体推迟及旧文档中一律逐群询问的方案。稳定群 ID 去重；母群、排除群、已分配群不得加入。首次枚举先建立基线，暂时漏读后重新出现不能当成新群。若宿主不能可靠辨认新加入，只能称“新发现的群”，显示真实能力，不伪称已验证加入时间。

自动加入仅影响后续内容使用的配置，不扩充已冻结当前消息的发送范围。轻提示汇总数量，详细结果按需查看，不逐群刷屏。

人工排除保存后自动从配置分组删除，不要求用户逐组删除；不自动补位、不重排其他目标。空组从可执行配置移除，历史记录保留。解除排除不自动恢复进组；需要明确重新分配。

当前任务尚未尝试的排除目标要阻止派发并持久记录人工排除；已经提交或在途无法撤回。不可直接删除运行/历史行。实现时以独立撤销授权/跳过记录与冻结快照兼容，不能破坏现有 allocations 与 deliveries 一致性检查。排除保存和 claim 必须有确定的原子顺序，避免界面显示排除成功后仍发起新的提交。

清理入口不等于删除内部校验、诊断、账号隔离、持久去重、异常保护或自动化测试；也不能清除旧测试占位及运行记录。运行诊断和导出日志保留在维护分区。

## 13. 双来源消息库与资源管理增补（待实现）

日期：2026-10-22。用户确认主要类型为文字、图片、视频，其他类型为增强功能；群同步不移除。消息库、双来源及胶囊联动一起规划，不另做第二套群发引擎。本节不改变当前 1–20 群发送上限、前台要求、手动开始/继续及失败/未知不自动重试规则，不宣称 Mikoto 菜单或其他类型接口已验证。

### 13.1 两条内容入口，共用执行主干

- 群同步：保留母群、来源成员及类型过滤，符合条件的新消息进入当前内容，再由用户选择分组开始。
- 消息库：用户可在私聊或群聊中明确选择消息并“保存到消息库”；不受群同步的母群/来源成员限制，不自动收集任意聊天。长按菜单为目标交互，须核验宿主菜单接入能力；不支持时明确说明。

- 转发来源可选 `group_sync` / `message_library`。库模式不启动群同步监听，不要求配置母群/来源成员，仍校验账号、所选内容、素材和目标规则；群模式继续检查来源配置及可信新消息证据。
- 两入口经来源各自校验后汇入内容计划，复用目标分组、节奏、runner、投递记录、暂停/继续/取消；新增来源身份和库内创建计划入口，不伪造群 ID/服务器消息 ID 来绕过现有校验。
- 每账号仍只占用一份当前转发内容/一个活动执行。保存其他消息到库不替换当前内容、不自动发送；未结束内容或活动任务期间拒绝切换当前来源模式，须明确结束并等在途收尾。过期捕获回调不得进入库模式任务。

### 13.2 内容、素材与发送任务分离

- 消息库条目具有稳定 ID 和不可变内容版本；每次明确选择并开始一次新群发时建立独立任务及幂等操作标识，不用修改旧任务/删除旧 claims 实现再次发送。
- 创建计划时冻结所选版本和目标范围，后续编辑或删除库条目不改写在执行内容。重复点击同一次确认不创建多个任务。
- 文字、静态图片、视频为主要支持目标。逐类型完成导入、独立快照、实际预览、发送构造及真机验证后才开放；文件、链接、名片等按能力扩展，不能将“任意聊天可导入”宣称为“所有消息类型已可发送”。
- 通用素材层将来源授权/账号引用与实际文件分离。同账号相同字节按 SHA-256 精确复用，存储去重不阻止新消息/新任务的转发。微信压缩或重新编码后的不同字节不保证去重，不按相似图片自动替换。
- 消息库条目、群同步预览、已冻结计划、活动运行及保留历史的素材引用共同参与生命周期管理；清理不能只扫描当前计划。旧随机 UUID 图片引用需兼容迁移，不能突然被当作孤儿删除。

### 13.3 设置页资源管理与容量边界

用户要求：资源管理正式纳入插件设置页，容量达到 80% 开始提醒可删除部分资源，不能等满额失败才发现。

- 在设置页新增“消息库与资源管理”入口，显示实际已用容量、总限额、占用比例/进度、剩余空间及可回收容量；可查看按大小/时间整理的资源列表、类型、引用/使用中状态，并提供清理入口。不只在诊断里显示。
- 沿用现有图片资源预算作为首期通用自有媒体总预算：256 MiB（268435456 字节，界面标清单位），不是每类各 256 MiB，也不是每账号额外增加一份。包括自有群同步快照、库内媒体、预览/派生媒体和临时暂存；共享文件按实际物理字节只计一次，预留中的新增空间单列且计入接纳判断。
- 现有图片单文件 20 MiB 限制不自动取消；视频等类型需另定单文件、时长/格式及内存限制。视频采用有界分块导入，不整段载入内存；不提供无上限容量选项。
- SQLite 文字/元数据和诊断空间另行说明，不冒充媒体预算内的全部磁盘使用。微信自身聊天媒体不在可清理范围，界面说明“仅管理 SyncRelay 自有资源”，不承诺控制微信缓存总量。
- 当前资源目录跨账号共享预算；汇总容量不能泄露其他账号的文件名/正文/缩略图，只允许管理当前核对账号有权操作的条目。不能读取/统计时显示“容量暂不可用”，不显示虚假 0 或空库，也不据此放宽配额。

### 13.4 80% 提醒、满额及写入失败反馈

- 以真实字节判断达到或超过 80%（约 204.8 MiB），不以四舍五入后的显示百分比提前/延后判断；设置页持续显示接近上限提示：“资源占用已达 80%，可清理不再使用的资源”。阈值为明确需求，不依赖用户先打开诊断。
- 胶囊/运营首页给出一次轻提示及“管理资源”入口；不遮挡暂停/继续等主要操作，不展示文件名或内容。总开关关闭时不额外强行弹出胶囊，设置页/消息库及下一次前台可见入口仍显示警告。不承诺后台系统通知。
- 提醒需跨页面刷新及重启抑制重复，不能每条消息/每次 tick 弹窗。建议默认采用回落到 75% 以下后再次到达 80% 才重置提醒资格；持久提醒周期按共享仓库记录，界面常驻警告不因已提醒而消失。此回落值为待交互验收的默认细节。
- 未到 100% 但新素材会越过剩余预算时，同样明确拒绝本次新增写入，提示“空间不足，需释放约 X MiB”并直达资源管理；不只报捕获失败。精确去重且无需新增存储的复用不应被简单按“已满”拒绝，但需要派生/暂存的新空间仍须计入。
- 总配额、设备磁盘不足、单文件超限、读取失败及写盘失败分开提示；失败不得发布可用库条目/内容，也不应新建发送任务或误显示发送失败。保留用户可重试的状态，不因清理完成自动重发。
- 导入/捕获/派生写入需串行或原子预留容量，分块过程中持续执行预算约束；失败回滚引用并清理自有临时文件，进程中断遗留在恢复时安全回收，不出现并发各自通过检查后一起超额。

### 13.5 删除与清理安全

- 显示可回收容量及删除范围并要求明确确认；提供删除库条目、清理无引用临时/孤儿素材的区分。共享资源只有最后有效引用解除后才能释放，删除条目数不等于释放文件数；结果展示实际释放字节。
- 正在导入/预览/发送或被未结束任务引用的素材不得物理删除。历史仍需重放/预览的素材不能被静默淘汰；若后续提供释放已完成历史素材，须明确提示原历史将不可预览/重发，保留摘要和所有发送账本。
- 配额达到上限不自动删除用户资源、不清空计划/claims 换空间、不猜测并删除微信文件。引用损坏或归属无法核对时保守保留并提示维护，不能视作无引用。
- 清理、导入及发送准备之间建立引用/占用保护和确定事务顺序，防止刚校验可用的素材被同时删除。清理后刷新设置页、库列表及胶囊同一份容量快照，不恢复旧任务派发许可。

### 13.6 胶囊联动与阶段验收
- 沿用唯一胶囊：群模式空闲为“等待群消息”，库模式空闲为“选择库内消息”；内容就绪后共用待转发、运行、暂停、完成等投影。全部结束后群模式按既定策略恢复监听，库模式回到待选择并保留完成摘要，不自动取下一条库内容。
- 容量状态作为独立告警投影，不冒充发送业务状态；达到 80% 不暂停已有任务，空间不足只阻断需要新增素材的操作，不全局阻断无需新增资源的文字/已就绪素材执行。真实素材缺失等错误仍沿用原安全门禁。
- A：先补双来源身份、库条目/版本、引用与配额预留、提醒周期及旧资源兼容契约；不把本节写入文档当作 schema 或代码已经迁移。
- B：设置页来源选择、消息库管理、容量页面和胶囊状态/告警；C：主动导入、库内计划入口、通用素材仓库及文字/图片/视频分类型适配和联动；D：完整真机验收。其他类型按能力单独标注，不能阻塞主类型而伪报全部通过。
- 必测：私聊/群聊显式导入且不发送；删除原聊天后库内可用；同图多次导入只计一份；同素材多次任务独立且双击幂等；编辑不改旧任务；跨模式旧回调失效；重启引用保留；80% 字节边界、提醒抑制及回落重置；未满但新文件超额；满额精确复用；并发预留、设备磁盘满、分块失败/中断回收；容量统计失败；共享/跨账号引用隔离；删除在用素材拒绝；清理不删 claims/微信文件、不自动继续发送；关闭总开关时仍可见容量问题。

## 14. 消息库类型范围与兼容策略定稿（2026-10-22）

日期：2026-10-22。用户确认的消息库类型范围。本节只确定范围与契约，**不提前实现**任何新类型、不进入 UI、不改发送 ABI；冲突时以本节对类型范围的表述为准，其余仍按第 12、13 节。

### 14.1 首期与后续类型

- 首期支持：**文字、静态图片、视频**。三者按同一底座接入，逐类型补齐能力后才对该类型开放入口。
- 后续计划扩展（不要求首期实现）：文件、链接、名片、自定义表情、语音等。列举即为计划，不是承诺的时间或顺序。
- 群同步（母群 + 来源成员 + 类型过滤）保留，不移除；消息库不是替代品。
- 其他类型在任何阶段都不得被当作文字兜底导入或发送。

### 14.2 通用底座，不按类型复制

- 库条目（稳定 ID）、不可变版本、冻结任务、素材引用、配额与预留是**通用底座**，所有类型共用一套表、一套任务身份、一套引用与容量账本。
- 各类型只在四个位置各自负责：**payload 校验、素材准备、预览呈现、发送适配**。禁止为某个类型复制 item/version/task/引用/配额表，或另建一套任务 ID。
- 发送主干（分组、节奏、暂停/继续/取消、投递记录）继续共用；类型差异止于“如何准备一份可发送内容”。

### 14.3 三个能力位，不用一个 supported 掩盖缺口

每个类型分别给出三个独立、可分别取假的能力位，取值只能来自已完成的实现与证据，不能由类型名称推断：

- `importAvailable`：能否把该类型导入为库条目并写入不可变版本。
- `previewAvailable`：能否在库里如实预览该类型的实际内容。
- `dispatchAvailable`：能否把该类型的冻结任务真正派发。

规则：
- 三者互不蕴含：`importAvailable=true` 不代表可预览，更不代表可发送。
- 未实现的能力位必须为 false，并在入口处明确显示不可用原因；不得用“支持该类型”一句话概括。
- 当前记录（2026-10-22，本仓库状态）：文字与静态图片的可导入已实现，其导入与素材链路的原生测试已在 macOS 隔离快照内编译、链接并三轮执行通过（仍为 Foundation/模拟对象，不是真机或宿主语义）；库内容派发对**所有**类型均未实现；视频三项均未实现；UI 未开发。任何一项都不得对外宣称已支持。
- 库条目的 `kind` 与版本 `kind` 是**数据**，不是能力声明；能力位由类型注册表在运行时给出，缺失类型按“不支持”处理。

### 14.4 类型与 payload 格式版本

- 每个类型有自己的 payload 结构与格式版本。图片 payload 现有 `snapshotSchema`（当前 1）；文字 payload 目前无版本字段，**缺省视为版本 1**（只做向后兼容解释，不据此新增写入字段）。
- 写入端只写“当前版本”；不就地升级历史版本（版本不可变）。需要新格式时显式新建一个版本，旧版本保持原字节。
- 读取端维护“已知版本集合”：
  - 已知版本 → 按该版本解释，行为与写入时一致；
  - 未知版本或未知类型 → **保留记录**，明确拒绝预览/派发，`previewAvailable=false`、`dispatchAvailable=false`，不猜测字段、不降级成文字；
  - payload 损坏 → 与未知版本同样处理，不删除记录、不改写字节。
- 版本与能力的判定都必须可回读（重新读库核对），不能只信任导入时的内存标记。

### 14.5 未支持类型的拒绝语义

- 导入：在写入任何条目/版本/素材引用之前拒绝，返回明确原因；不产生半成品条目。
- 预览：明确显示“该类型暂不支持预览”，不回退到正文/文件名/占位文本冒充内容。
- 冻结与派发：拒绝建立冻结任务或拒绝派发，**不得**把未知 payload 当文字发送，也不得静默改为“仅发送标题”。
- 拒绝不删除既有记录：已存在但当前版本不支持的类型条目继续列出，可删除，但不可预览/派发；历史任务与发送账本不动。
- 诊断只记录类型标识与固定原因码，不记录正文、文件名或路径。

### 14.6 约束扩展与旧数据迁移

- 当前 `library_items.kind` / `library_versions.kind` 的 CHECK 仅允许 `text`、`image`。新增类型必须**保留旧数据**：不清库、不重建业务账本、不取消既有必要校验（不可变版本触发器、唯一键、账号隔离、冻结触发器）。
- SQLite 不能直接修改 CHECK，采用单事务内“建新表 → `INSERT ... SELECT` 原样复制 → 删除旧表 → 重命名 → 重建索引与触发器”的标准重建流程；重建前后核对行数、主键、版本序号与 `foreign_key_check`，失败整体回滚。
- 由于 `library_tasks`、`plan_sources` 通过外键引用 `library_versions`，重命名/删除父表期间必须在事务外关闭 `PRAGMA foreign_keys`，事务内完成后 `PRAGMA foreign_key_check` 通过再提交并恢复开启；顺序与回滚点写入迁移用例。
- 触发器一律 `DROP ... IF EXISTS` + `CREATE`（见 14.7），避免旧库保留旧定义。
- 本轮不执行任何 kind 扩展迁移；这里确定的是将来实施时必须遵守的约束。

### 14.7 已发现并修正的迁移陷阱

`CREATE TRIGGER IF NOT EXISTS` 不会替换已有同名触发器：已存在的 schema 13 开发库会永久保留旧定义。A-3 返修已改为在迁移事务内 `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER`，使源码成为唯一定义来源，且不重建表、不改写任何行。后续修改任何库表触发器都必须沿用这个做法。
