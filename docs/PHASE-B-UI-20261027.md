# Phase B UI slice (2026-10-27)

This change starts Phase B with a bounded UI slice. It does not open Phase C
automatic capture, new-group enrollment, resend, backup/restore, or any new
message type.

## Included

- A projection-only `SyncRelay 运营` home page reached from the operations capsule.
- Stable routing from the home page to the existing preview, confirmed-plan,
  group, rule, history, and exception screens.
- Capsule states for waiting, ready-to-forward, running, paused, in-flight,
  and completed content, with an explicit menu.
- Capsule actions for opening the operations home, entering settings, dropping
  a preview, pausing/continuing a run, and cancelling a run. Cancel keeps the
  displayed account and run identifiers captured before the confirmation.
- Edge snapping and safe-area/keyboard-aware placement remain bounded subview
  behavior; no extra window or touch interception is introduced.

## Not claimed

- The new page is not a device visual acceptance result yet.
- Opening the page never arms capture, creates a plan, or sends a message.
- Automatic capture, persistent always-on operation, new-group assignment,
  resend, backup/restore, batch expansion, image/video dispatch, and delivery
  confirmation remain closed.

## Entry wiring round (2026-10-27, pre-commit verification snapshot)

Device feedback on the `2cb8f4d` package showed the operations home was not
reachable: the idle floating entry still opened the settings panel, and the
home painted a "打开设置" row without a route. The capsule body also refused
its tap whenever the action was `open`.

This round changes only the entry wiring. It does not touch `Adapter/`,
`Core/`, the database or the schema, and it does not change capture gating,
generation, server ID handling, source-time semantics or sending.

- **Idle entry.** The existing floating entry now opens the operations home
  through the same presenter resolution and account binding the capsule uses.
  It is the same single button, with the same appearance, drag behavior,
  safe-area placement and show/hide rules; no second floating button and no
  extra `UIWindow` were added. No `ready`/`completed` state is fabricated to
  force a capsule: the home shows its own empty state instead. The WeChat
  settings entry to `SyncRelay 转发` keeps working unchanged.
- **Settings route.** The home's "打开设置" row calls an explicit
  `openSettings` callback supplied by the caller. The callback is bound to the
  account captured when the home was opened and re-verifies it, so a changed
  account refuses the old page instead of silently switching. The settings
  panel is built from the same shared `store`/`capture`/`session` objects, so
  there is no parallel state source, and it is stacked on the home's own
  navigation controller: closing it returns to the home instead of dismissing
  the whole modal. Its save, close and unsaved-draft guard semantics are
  unchanged.
- **Settings panel lookup.** Because the settings can now be reached as a
  pushed page, the presented navigation is no longer always rooted at the
  settings panel: the home is its root in the home→settings stack, while the
  standalone settings entry is rooted at the panel itself. The three
  environment guards that need the settings state therefore locate the panel
  by its type anywhere in the stack instead of reading the root controller, so
  they read the real `dirty`, idle-timer, experiment and countdown values.
  Pushing a sub-page (group picker, content viewer, plan list) does not move
  the root controller. The lookup returns nil when no settings panel is shown,
  which keeps the previous "no panel presented" behavior.
- **Route lifetime.** The navigation controller is captured weakly by the
  settings callback, because the navigation owns the home and the home owns
  that callback. The callback fetches the navigation back at call time and
  refuses to route when it is no longer the navigation this entry manages.
- **Repeated requests.** The route refuses a navigation that is not the one the
  entry presents, a stack whose visible page is no longer the operations home,
  a stack that is presenting or dismissing, and a settings panel that is
  already on the stack, so a repeated tap cannot create a second settings
  page. The home is the root controller of the stack, so pushing a page above
  it does not move the root; the check compares the home against the top of
  the stack instead. A managed stack that holds only the home, with a valid
  account and no transition, is allowed through to create and push the
  settings panel. These are refusals only; no guard was relaxed and no check
  was removed.
- **Capsule body.** The body tap opens the home for the waiting, ready and
  completed states; the previous `action == "open"` guard is gone. The side
  "查看" button and the menu keep their own behavior, pause/continue still
  runs its original action, button and menu touches stay excluded from the body
  tap, and the tap now waits for the pan to fail so ending a drag can never be
  reported as a tap.

Opening the home still never arms a receiver, starts a source-time probe,
confirms a plan, restores a run, sends or retries anything, and no lifecycle
callback starts capture or sending.

## Verification

- The focused Phase B Python contract suite passes (`21` tests, `16` of them
  new across the entry round, the review round and this final fix), and the
  complete local Python suite passes (`282` tests).
- The new contracts were red/green checked: with the old entry routing, the
  old missing settings route and the old capsule guard in place, the matching
  contracts fail; they pass with the fix. A simulated regression that
  dismisses the stacked settings panel instead of popping it is also caught,
  and reverting the stack lookup, the weak navigation capture and the repeated
  request guards each fails the matching contract.
- The home/top comparison is checked by executing the guard's own logic
  against both stack shapes: a managed stack holding only the home must be
  allowed through to the settings push, and a home that is not the visible
  page must be refused. Restoring the reversed comparison makes both the
  positive and the direction contract fail.
- **Layers, kept apart.** The stack lookup, the route lifetime, the repeated
  request refusal and the home/top comparison are covered by source contracts
  plus a logic check that evaluates the guard conditions; the Python suite
  itself exercises no UIKit code. Nothing here is a UIKit behavior result: the
  navigation stack contents, the transition state and the resulting page
  order can only be observed by a native build and a device run.
- `py -3 -m compileall -q tools tests` passes and `git diff --check` is clean.
- The cached libclang double-architecture syntax check passes (`106` units,
  arm64 and arm64e, no diagnostics). This is a syntax layer only.
- **Not executed on Windows:** Objective-C native compile/link and execution,
  the macOS CI build, DEB packaging, installation and real iPhone UI
  behavior. The source contracts and the syntax check must not be described as
  those results. The stack lookup, the navigation lifetime and the repeated
  request refusal are source-level contracts here; only a native build and a
  device run can show the UIKit behavior.
