# 消息类型一次采样

本轮接收候选仍只把文字和静态图片转成可预览源消息。视频、名片、语音、表情、文件/链接等类型不会因为数字类型出现就被转发，也不会调用未知资源 getter。

## Mikoto 证据边界

离线快照能看到 `receiveMessageWrapWithType1/3/34/42/47/49/1000` 这些分支；其中只有 type 1 的 `m_nsContent` 文字读取和 type 3 的 `getMsgHdOrMiddleImg:` 图片读取得到过 payload 级证据。快照里的 `sendVideoMessage...`、`sendCardMsgWithShareUser...`、`AddAppMsg:` 和 `AddVideoMsg...` 是发送辅助方法，不是接收 ABI 证明。不要把常见枚举直接写成“43=视频”或“42=名片”。

## 设备步骤

1. 选择一个授权测试母群和一个确定的来源 wxid，只勾选“文字”，保存后点击“开始等待（不发送）”。这样未知媒体不会进入图片等待，最后的文字可用来结束本次采样。
2. 在母群依次由同一个来源发送一条新的：语音、名片、表情、视频、链接/文件（能发送的类型才发送）。每条之间等待回到群内，避免重复点击；不要用历史转发或撤回补同步消息替代。
3. 最后发送一条普通文字。它只用于结束等待并显示预览，不会发送到任何目标群。若不想建立预览，也可以在前几条之后手动取消等待再导出诊断。
4. 返回 SyncRelay，打开“适配诊断”并导出报告。查看 `receiveCandidate.messageTypeProbe`：
   - `rows` 是去重后的 `{type,count}`，最多 32 种数字类型；
   - `sequence` 是最多 64 个数字回调顺序，可按发送顺序与 `rows` 交叉核对；
   - 这里只记录合法来源会话的数字类型，不含账号、群 ID、正文、XML、文件路径或媒体内容。
5. 把报告和发送顺序一起保存。一次混合采样只能得到“某个回调对应的数字”，不能单独证明 payload 语义；要实现视频或名片，下一轮仍需针对实际数字验证资源 getter、快照 schema、预览、发送构造器和自有消息回读。

如果 `rows` 为空，先确认回调方向、来源 wxid、母群和服务器消息 ID 均正确；不要据空报告猜类型。诊断采样不会放宽现有文字/图片过滤，也不会改变微信原接收实现。
