# 分组补位与自定义分组（2026-10-28）

本轮只改「配置侧分组」：新群出现时，自动分组会把它们补进未满的**自动**规则，而不是
每次都新开一条碎片规则。**不涉及**冻结计划、计划/运行/交付表、发送路径或 schema。

## 1. 为什么改

旧行为：`SRGroupPlanner` 把「已分配」的群全部排除，只在末尾追加新规则。于是「17 个群的
分组 + 4 个新群」会得到一条 4 群的新规则，而不是补到 17 那条。用户既要确认结果对，也要
知道该点。

## 2. 规则来源（草稿 JSON 字段，无 SQLite 迁移）

配置本来就以整份 JSON 存在 `configurations.payload`，因此新增两个**可选**的规则键：

| 键 | 取值 | 含义 |
| --- | --- | --- |
| `rules[].origin` | `"auto"` / `"custom"` | 缺省视为 `auto`（历史规则由生成器产生） |
| `rules[].capacity` | `100` / `200` | 分组规格；`custom` 规则不得携带 |

`SRConfiguration validateDraft:` 只接受上述取值；`custom` + `capacity` 组合、非 100/200
的容量、`@YES` 之类布尔容量都会被拒绝。旧配置（两个键都没有）仍然有效。

## 3. 补位语义

- **只补自动规则**：`origin != "custom"` 且目标数少于目标的规则。
- **目标 = min(规则规格, 调用方传入的执行上限)**。规划器自身不含任何上限常量。
- **顺序**：按规则 position 从上往下；补满再下一条；补位先于新建，因此新规则只使用补位
  之后剩下的群。
- **自定义分组永远不补**：它是刻意拼出来的集合，哪怕只有 3 个群也保持原样。
- **不修改输入**：预览返回新配置，原草稿逐字节不变（原生测试锁定）。

### 3.1 两种操作意图在 Core 区分

`SRGroupingIntent` 决定是否补位，UI 只是选择意图，不再用配方字段暗示：

| 意图 | 入口 | 补位 | 生成规则的来源标记 |
| --- | --- | --- | --- |
| `SRGroupingIntentAutomatic` | 自动分组 | 先补自动规则，剩余群再新建 | `auto` + `capacity` |
| `SRGroupingIntentCustom` | 手动选择群聊 | **完全不补**，所选群全部留给本次新建 | `custom`，无 `capacity` |

因此「手选 2 个群」不会被旧自动规则先吃掉；即使手选数量超过旧规则缺额，所选群也不会被
拆走。同一条自动规则在自动意图下仍会照常补位——差异来自意图，不是数据。

### 3.2 空池与纯补位的返回契约

| 请求 | 池 | 结果 |
| --- | --- | --- |
| 生成条数 > 0 | 空池或只有母群 | **合法零分配预览**（`generatedRuleCount=0`、`assignedCount=0`）；UI 提示「没有变更」，草稿不变 |
| 生成条数 > 0 | 有可用群 | 正常分配 |
| 生成条数 = 0（纯补位） | 有可补规则 | 只补位 |
| 生成条数 = 0（纯补位） | 无任何可补规则 | **明确拒绝**（无变更），不返回空预览 |

已知交互（有意如此）：从自动规则里**排除**若干群后，该规则会再次低于目标，下一次补位会用
其它未分配群把它补回。若要让某条规则保持固定规模，请把它改为自定义。

预览新增字段：`topUpRules`（每条 `ruleID/name/before/after/added/capacity/target`）、
`topUpCount`、`topUpRuleCount`；`assignedCount` / `shortfallCount` 仍然只统计**新建**规则，
保持既有语义。

**纯补位**：自动分组的两项条数都填 0 即「只补位、不新建」，补不进去的群保持未分配，
不会为了凑数生成碎片规则。两项都为 0 且没有任何规则可补时会被拒绝（无变更）。

## 4. 执行上限不是设计常量

测试期单条规则可执行 1–20 群，**这个 20 只用于测试**。它只作为参数传入：

```
[SRGroupPlanner previewWithRows:… recipe:… executionLimit:SRRunProjectionTargetLimit error:…]
```

补位目标因此是「规格与当前闸门的较小值」：现在补到 20，闸门放开后同一条规则继续补到
100/200，**不需要改配置、不需要迁移数据**。

放开闸门时只需要改这几处（都是同一个数字）：

| 位置 | 作用 |
| --- | --- |
| `Core/SRStore.m:435,555,586,1205,1313` | 计划/运行/冻结任务的授权范围 |
| `Core/SRRunProjection.m:21`（`SRRunProjectionTargetLimit`） | 页面投影与补位传入值 |
| `Adapter/SRSmallGroupSession.m:248`（`targetLimit`） | 会话状态上报 |
| `Core/SRRelayCoordinator.m:388` 及 UI 文案 | 提示文字 |

`capacity` 只写 100/200，测试期的 20 不会进入任何持久化数据。

## 5. 入口变化

- 「自动分组」以 `SRGroupingIntentAutomatic` 调用，生成的规则 `origin=auto`，带 `capacity`
  （100 或 200）。
- 「手动选择群聊」以 `SRGroupingIntentCustom` 调用，生成的规则 `origin=custom`，不带
  `capacity`；语义变为「自定义，不参与补位」，不再只是「按 100 切分」。
- 设置页规则行显示 `N 个群 · 自动，补位到 100` 或 `N 个群 · 自定义，不参与补位`。
- 规则菜单新增「改为自动分组（参与补位）」/「改为自定义分组（不参与补位）」，可逐条互转。

## 5.1 历史兼容边界（不声称识别出来源）

旧规则没有 `origin`，而**缺失本身不能证明它当初是自动选择**：旧版「手动选择群聊」也走
100 规格的生成器，历史数据里两类规则看起来一样。

因此本版的处理是：

- 缺省按 **auto 默认策略**处理（可以参与补位），这是**默认策略**，不是"识别出了旧规则
  来源"的结论；
- 不迁移、不改写任何历史计划或冻结快照；`origin` 只在用户保存配置时写入草稿 JSON；
- 想把某条旧规则固定下来，在设置页把它改成「自定义」即可，改动只影响后续内容。

## 6. 明确未做

- 没有「新群提醒」：胶囊徽标、后台检测、打开即提示都未实现，属于后续视觉与阶段 C 范畴。
- 没有自动触发：补位仍由用户点「自动分组」发起，确认后还需「保存」。
- 不修改已冻结计划；补位只影响之后捕获并确认的内容。

## 8. 设备反馈（2026-10-28）

用户在本机安装 `0.2.21`（源码 `7e516a8`，run `40606626728`，SHA-256
`e861353a94b503cd1d094bbed3cf8a7af5dae86d2543336e4c5b88ad5c34f445`）后反馈：增量清单
**测试通过** —— 自动纯补位、自定义不补位、手选目标完整保留、取消预览不改草稿、保存后重开
仍保留分组类型。

一次中间尝试曾观察到「17 群未变、另建一组 4 群」的旧行为，随后重新安装即恢复正常。**其
原因未证实**：可能是旧二进制仍在运行，也可能是当时走的是「手动选择群聊」入口，或查看的是
已冻结计划而非草稿配置；三者都未被实际取证区分。因此本文档**不**断言"同版本包必然被安装
器跳过"，也不把该次现象归因为产品缺陷。

可复现的判别方式留作经验：新版规则行会显示 `自动，补位到 100/200` 或 `自定义，不参与补位`，
旧版只显示 `N 个群`；诊断导出的 `build.commit` 是唯一的包身份依据。
