# 便捷的规则内自动执行

日期：2026-10-21。产品基线：用户不接受把开发阶段的复核、观察和实验开关变成日常使用负担。正常规则执行不要求逐群确认收到，也不要求先做接口检查或导出诊断。

## 用户流程

1. 统一保存母群、来源成员、文字/图片类型和随机间隔，只选不需要发送的排除群；插件按 100/200 群规格自动分规则。
2. 手动等待并确认一条源消息。该内容供本计划全部规则复用，不为每个目标或每条规则重新抓取。
3. 对想执行的那条规则点一次“开始”，内部自动核对账号、目标、资源和发送接口，按节拍串行处理整个规则。不逐群弹窗，不逐群要求确认送达。
4. 用户可随时暂停、手动继续；微信重启后只需选择“继续未发”，不重新配置或复核所有已尝试群。恢复先等待一个新间隔，不补偿性连发。
5. 当前规则结束显示实际记录的完成时间和汇总。下一条始终由用户决定何时点开始，不自动接力。

进度主要展示已处理/总数、已提交、失败及结果未知数量。默认只按需列异常，不刷满每个已提交群。诊断导出保留给维护使用，不是开始、继续或完成的前置条件。

开发时少量测试群的验收不等于产品需要逐群人工确认；当前单群实验的默认关闭和二次确认仍是已交付测试包的边界，不能因此把长期产品也设计成一堆实验步骤。

## 自动处理与真实结果

- **已提交**：适配器已经核对实际宿主调用和身份，取得提交证据，可以继续排队的下一个群；不表示目标群已确认收到。
- **确认送达**：必须有可靠的关联回执。不能仅凭发送方法返回、status 数字或非零服务器 ID 自动写入。
- **明确的目标局部失败**：例如有依据证明某个目标已不可用，保留失败记录并跳过，不要求用户逐个处理，不自动重试该群。不能把账号、服务、网络不确定或平台限制猜成普通目标失败。
- **真正结果未知或执行环境异常**：保留当前尝试，停止后续派发；提示一次清晰的异常原因。用户之后点一次“继续未发”时只处理 pending，不重发已提交、失败或未知的群，不要求先逐群复核。
- **执行完成**：本条队列已处理完，而不是承诺所有目标均已送达。汇总保留失败/未知数量，不能把异常抹掉或把“已提交”偷换成“成功”。

自动检查、有限精确身份读取和资源生命周期管理放在插件内部，不需要用户盯着“观察中”。随机节拍控制范围和速度，不保证不会触发平台限制；明确限制必须停止，不能自动绕过或切下一条规则继续。

## 本轮已实现的核心

后续开发版本为 0.2.17，本轮尚未打包；手机上的 0.2.16 不包含这些改动。

- schema 6 只增加 `submission_receipts`，不重建或删除原表，不清已有实验占位、计划、配置或媒体引用。该表只存内部 delivery/attempt 和提交时间，不存聊天内容。
- 提交证据与实际投递结果分离：原 delivery 保留 uncertain，事务性增加提交记录；统计投影为 submitted，而不是 confirmed。重复回调不会重复记账或擦掉提交证据。
- runner 接受 submitted 后按已有节拍继续下一个 pending；正常规则不再因缺少自动送达回执而逐群要求人工介入。
- 暂停期间有在途尝试时先等其完成/超时，不能一边重置调度一边再次派发。中断在途尝试恢复为 uncertain，其他 pending 保留；重启不会自动开始发送。
- 用户明确继续后只 claim 从未尝试的 pending，未知/失败目标从不回到 pending。环境恢复本身不自动续跑。
- 队列耗尽自动记录 completed 和结束时间，包括存在异常的情况；不要求再手动“收尾”，也不自动启动下一规则。重启时最后一个在途尝试变未知但没有剩余 pending，可结束本条处理并保留异常。
- 历史页区分已提交与确认送达，异常页排除普通提交记录，不加入逐群人工核对按钮或人工修改成功的流程。

## 仍需接入

上述是存储、调度和记录展示的自动进度基础，不代表真机已具备多群发送。现有已验证文字/图片 host 和单群 UI 实验保持不变，仍未向真实规则 runner 提供 submitted 回调。

后续要实现并测试受限的小规模实际 transport、主线程调用与取消代次、统一的前台/常亮生命周期，以及规则开始/暂停/继续入口。适配层必须有真实提交证据才返回 submitted；不得把旧单群 host 的所有 uncertain 返回值直接转换为 submitted，尤其不能忽略构造失败、图片装载异常、账号变化、代理契约失败或观察身份冲突。

完成这一接入后再安排一次少量授权测试群的真机验证，正常测试也只需启动一次、结束后反馈整体结果，不要求逐群操作。100/200 群仍在后续渐进验收范围内，不直接一次开放全部群池。
