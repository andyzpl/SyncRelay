# 捕获与调度核心（开发中）

本模块只接收规范化消息和抽象发送器。尚未接入微信消息 hook、实际发送 API、执行按钮或应用生命周期驱动；插件启动不会创建 runner 或发送消息。

## 源消息流程

```text
配置草稿 -> 手动 arm -> 等待匹配 -> 冻结单条 preview -> 用户确认
    -> 同一事务写入源消息去重键、计划、全部规则、全部目标 -> 等待手动执行
```

`SRSourceCapture` 先冻结来源和分组配置，随后严格匹配账号、母群原始 ID、来源 wxid 和允许类型。昵称不参与判断，缺少明确的 `generatedByRelay = false` 来源标记不接收。第一条匹配后立即停止接收，后续消息不替换预览；确认后只建立计划，不自动开始任何规则。

规范化 envelope 字段：account、group、sender、messageID、type、generatedByRelay、payload。
文字 payload.text 必须是非空字符串；图片 payload.mediaReference 是不透明的媒体引用，不代表文件已下载或可发送。后续真实适配器负责来源 ID/类型核实、媒体准备及确认依据。

`messageID` 必须由接收适配器提供可稳定去重的源消息标识；目前未实现微信本地 ID 与服务器 ID 的合并，不得把临时 ID 当作已验证服务器标识。

数据库 schema v3 新增 source_claims，唯一键为 (account, source_group, message_id)。保存失败完整回滚，预览保留可重试；同源消息再次捕获不新建重复计划。用户明确“重新执行”走已有规则的新 run，不重新建立源消息 claim。

等待/预览目前仅在内存中，退出后需要重新捕获确认；已确认的计划与执行进度在 SQLite 中。预览并未被伪装成已持久化的任务。

## 串行调度

`SRRunner` 将存储、SRPacing、单调时钟、随机数和 SRSendTransport 连接起来：

- 显式 activateRun 后才接受 tick；初次激活和手动恢复均先等待一个新间隔，不赶进度。
- tick 每次最多 claim 并提交一个目标；同账号进程内只能由一个 runner 持有调度资格，暂停不释放。
- 发送器必须非阻塞，并在 canSendForAccount 中核对当前账号及真实发送适配状态。当前只有测试用 FakeTransport，没有微信发送器实现。
- 适配器在 runner 的串行队列上被调用；就绪检查不能同步跳回正等待 runner 的主线程。未来应提供经过核对的线程安全状态快照，发送操作异步切到微信要求的线程并再次检查身份。
- 每次派发检查账号和环境可用性。环境恢复不自动续跑；只有用户再次明确继续才恢复。
- 使用私有串行队列处理状态与异步结果；结果落库按 delivery/attempt 关联。
- 当前确认超时为 60 秒的内部测试策略，不是微信协议值。超时仅进入 uncertain 并暂停，不自动重发。
- 暂停后已有在途消息仍可返回；迟到回调仅更新对应旧批次，不能启动下一条规则。
- 全部确认成功才自动记 completed；有明确失败且队列耗尽时暂停等待人工收尾，不伪报全部成功。
- 进程重启必须先调用存储恢复，中断的 submitting 进入 uncertain。新 runner 不会因读取旧记录而自动派发。

本次没有自动定时器、后台保活或常亮集成。未来生命周期驱动需要选择合适的 timer、接入可发送环境判断和人工控制；不能直接在主线程循环调用 tick 当作完整实现。

## 已覆盖的测试设计

- 同昵称不同 wxid、其他群/账号/类型、自动转发来源不进入捕获；只锁定第一条。
- 深拷贝快照不受外部可变对象影响；账号改变不能确认。
- SQL 触发器模拟目标入库失败，验证源 claim 和计划整体回滚后可以再次确认。
- 2000 个目标通过假时钟和模拟确认完成，检查随机节拍及无自动下一规则。
- 暂停互斥、环境恢复不续跑、第二个 runner 不抢占、超时、最终迟到成功释放资格、已结束批次回调隔离。
- 重启后旧在途任务未知、不盲重发；原有核心和读取适配测试继续运行。

这不是手机实测。队列/过滤核心测试通过不代表微信接口兼容、图片可转发或平台允许该发送规模。

2026-10-20 实际结果：流水线 39418093430 中原有存储测试、模拟读取测试及新增完整流水线测试各连续运行三次，全部通过；本机 arm64/arm64e 语法检查通过。所有打包/产物步骤均跳过。具体日志见开发进度文档。
