# 捕获与调度核心（开发中）

最新产品与实现变更（0.2.17 开发源码、尚未打包）：正常规则内自动执行，不要求逐群人工复核。存储与 runner 已接受独立 submitted 提交进度；暂停/重启后的继续只处理 pending，未知/失败不重发。队列处理完自动记录完成时间，completed 不再等于全部送达，异常仍保留。详见 `AUTOMATIC-RULE-EXECUTION.md`；原单群 host 尚未连接多群 runner，不能把核心模拟测试当成真机多群通过。

核心模块接收规范化消息和抽象发送器。8.0.79.35 已有一次本人文字捕获及手动发送观察证据；0.2.10 另提供默认关闭的单目标文字主机实验，不连接批量 runner 或规则执行按钮。插件启动不会安装接收 hook、创建 runner 或发送消息。接收候选只有手动等待时才安装，细节见 `RECEIVE-CANDIDATE.md`；主动实验边界见 `SEND-ADAPTER.md`。

## 源消息流程

```text
配置草稿 -> 手动 arm -> 等待匹配 -> 冻结单条 preview -> 用户确认
    -> 同一事务写入源消息去重键、计划、全部规则、全部目标 -> 等待手动执行
```

`SRSourceCapture` 先冻结来源和分组配置，随后严格匹配账号、母群原始 ID、来源 wxid 和允许类型。昵称不参与判断，缺少明确的 `generatedByRelay = false` 来源标记不接收。第一条匹配后立即停止接收，后续消息不替换预览；确认后只建立计划，不自动开始任何规则。

规范化 envelope 字段：account、group、sender、messageID、type、generatedByRelay、payload。
文字 payload.text 必须是非空字符串；图片 payload.mediaReference 是不透明的媒体引用，不代表文件已下载或可发送。候选接收层已编写原始群/账号/wxid/整数 ID 读取检查，但实际字段语义仍待真机核对；图片媒体准备和结果确认依据未实现。

`messageID` 必须由接收适配器提供可稳定去重的源消息标识；目前未实现微信本地 ID 与服务器 ID 的合并，不得把临时 ID 当作已验证服务器标识。

数据库 schema v3 新增 source_claims，唯一键为 (account, source_group, message_id)。保存失败完整回滚，预览保留可重试；同源消息再次捕获不新建重复计划。用户明确“重新执行”走已有规则的新 run，不重新建立源消息 claim。

schema v4 另增 text_experiments：单群实验调用前独立持久占位，同源跨重启不能再次实验，不把占位解释为送达；已有活动批次时拒绝实验。升级保留旧配置与计划，旧版不能降级读取 v4 数据库。

等待/预览目前仅在内存中，退出后需要重新捕获确认；已确认的计划与执行进度在 SQLite 中。预览页面展示捕获时冻结的配置，不以之后编辑的草稿冒充旧配置。等待期间修改草稿或离开前台会取消等待；账号核对失败也会停止。

`SRStore` 新增按账号限定的计划列表、计划详情、规则卡片、批次历史及异常分页查询，并补充相应索引。列表/历史不复制源正文，只有显式打开计划详情才读取源快照；查询不会创建、激活或恢复批次。规则顺序解锁仅为显示提示，未来开始操作仍必须由原有事务重新检查账号互斥和前序状态。

## 串行调度

`SRRunner` 将存储、SRPacing、单调时钟、随机数和 SRSendTransport 连接起来：

- 显式 activateRun 后才接受 tick；初次激活和手动恢复均先等待一个新间隔，不赶进度。
- tick 每次最多 claim 并提交一个目标；同账号进程内只能由一个 runner 持有调度资格，暂停不释放。
- 发送器必须非阻塞，并在 canSendForAccount 中核对当前账号及真实发送适配状态。runner 当前仍只有测试用 FakeTransport；独立的单群主机实验不等于已接入批量发送器。
- 适配器在 runner 的串行队列上被调用；就绪检查不能同步跳回正等待 runner 的主线程。未来应提供经过核对的线程安全状态快照，发送操作异步切到微信要求的线程并再次检查身份。
- 每次派发检查账号和环境可用性。环境恢复不自动续跑；只有用户再次明确继续才恢复。
- 使用私有串行队列处理状态与异步结果；结果落库按 delivery/attempt 关联。
- 当前确认超时为 60 秒的内部测试策略，不是微信协议值。超时仅进入 uncertain 并暂停，不自动重发。
- 暂停后已有在途消息仍可返回；迟到回调仅更新对应旧批次，不能启动下一条规则。
- 已确认提交（submitted）与可靠送达（confirmed）分开；目标局部失败记录并跳过，实际未知暂停后用户可一次继续未发，不逐群复核。全部目标已处理自动记 completed 并保留异常计数，不伪报全部成功，也不再要求人工收尾。
- 进程重启必须先调用存储恢复，中断的 submitting 进入 uncertain。新 runner 不会因读取旧记录而自动派发。

批量 runner 尚无实际 timer、后台保活或常亮驱动。单群实验单独实现 10 秒等待、最多 30 秒观察及活动期间常亮/退出恢复；不能把它直接当作规则 runner 生命周期或在主线程循环 tick 的完整实现。

## 已覆盖的测试设计

- 同昵称不同 wxid、其他群/账号/类型、自动转发来源不进入捕获；只锁定第一条。
- 深拷贝快照不受外部可变对象影响；账号改变不能确认。
- SQL 触发器模拟目标入库失败，验证源 claim 和计划整体回滚后可以再次确认。
- 2000 个目标通过假时钟和模拟确认完成，检查随机节拍及无自动下一规则。
- 暂停互斥、环境恢复不续跑、第二个 runner 不抢占、超时、最终迟到成功释放资格、已结束批次回调隔离。
- 重启后旧在途任务未知、不盲重发；原有核心和读取适配测试继续运行。
- 新增自动进度模拟：一次激活串行处理三个目标、submitted 不冒充 confirmed、正常提交不出现在异常清单、未知暂停后一次继续未发、目标局部失败自动跳过、环境恢复不自动续跑、提交记录事务回滚，以及 schema 5 加法升级保留旧配置/占位/中断进度。

这不是手机实测。队列/过滤核心测试通过不代表微信接口兼容、图片可转发或平台允许该发送规模。

2026-10-20 实际结果：流水线 39418093430 中原有存储测试、模拟读取测试及新增完整流水线测试各连续运行三次，全部通过；本机 arm64/arm64e 语法检查通过。所有打包/产物步骤均跳过。具体日志见开发进度文档。
